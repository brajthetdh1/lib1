Introduction to Terraform

What is Terraform?

Terraform is an open-source Infrastructure as Code (IaC) tool created by HashiCorp that enables you to safely and predictably create, change, and improve infrastructure using a declarative configuration language.

In traditional infrastructure management, system administrators manually configure servers, networks, and other resources through web consoles or command-line interfaces. This approach suffers from several critical limitations:

Traditional Approach Terraform Approach
Manual configuration Automated provisioning
Inconsistent environments Consistent environments
Difficult to reproduce Easily reproducible
Hard to version control Version controlled
Error-prone processes Reliable and repeatable

Key Characteristics of Terraform

Declarative Language

You describe the desired end state of your infrastructure, and Terraform figures out how to achieve it.

Cloud Agnostic

Supports multiple cloud providers (AWS, Azure, GCP) and on-premises infrastructure.

Resource Graph

Builds a dependency graph to determine the correct order of operations.

Execution Plans

Shows what actions will be taken before making any changes to infrastructure.

Core Concepts

1. Configuration Language (HCL)

Terraform uses HashiCorp Configuration Language (HCL), a declarative language designed for human readability while being machine-friendly.

Basic HCL Syntax Example 
# Define a provider
provider "aws" {
  region = "us-west-2"
}

# Define a resource
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1d0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer"
  }
}

2. Providers

Providers are plugins that Terraform uses to interact with cloud providers, SaaS providers, and other APIs. Each provider adds a set of resource types and data sources that Terraform can manage.

Cloud Providers

  • AWS
  • Azure
  • Google Cloud
  • DigitalOcean

Infrastructure Providers

  • Kubernetes
  • Docker
  • GitHub
  • DNSimple

3. Resources

Resources are the most important element in the Terraform language. Each resource block describes one or more infrastructure objects, such as virtual networks, compute instances, or higher-level components like DNS records.

Resource Block Structure 
resource "provider_type" "resource_name" {
  parameter1 = value1
  parameter2 = value2
  # ... additional parameters
}

4. Data Sources

Data sources allow Terraform to use information defined outside of Terraform, or defined by another separate Terraform configuration.

Data Source Example 
# Get information about an existing AWS AMI
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
}

5. Variables and Outputs

Input Variables

Parameters for Terraform modules that allow customization

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t2.micro"
}

Output Values

Return values from a module that can be used by other configurations

output "instance_ip" {
  description = "Public IP of the instance"
  value       = aws_instance.web.public_ip
}

Terraform Workflow

1

Write

Define resources in .tf files using HCL

2

Initialize

Run terraform init to download providers and set up backend

3

Plan

Run terraform plan to see execution plan

4

Apply

Run terraform apply to create infrastructure

5

Destroy

Run terraform destroy to remove infrastructure

Detailed Workflow Explanation

Initialization Phase

The terraform init command initializes a working directory containing Terraform configuration files. This is the first command that should be run after writing a new Terraform configuration.

  • Downloads and installs providers
  • Initializes the backend
  • Downloads modules (if any)

Planning Phase

The terraform plan command creates an execution plan, which lets you preview the changes that Terraform plans to make to your infrastructure.

  • Shows what resources will be created, modified, or destroyed
  • Highlights dependencies between resources
  • Provides a safety check before applying changes

Application Phase

The terraform apply command executes the actions proposed in a Terraform plan. It's the command that actually creates, updates, or destroys infrastructure.

  • Applies changes in the correct order based on dependencies
  • Updates the state file with the new infrastructure state
  • Can be automated in CI/CD pipelines

State Management

What is Terraform State?

Terraform must store state about your managed infrastructure and configuration. This state is used by Terraform to map real world resources to your configuration, keep track of metadata, and to improve performance for large infrastructures.

State File Contents

The Terraform state file (terraform.tfstate) is a JSON document that contains:

Resource Mapping

Links configuration resources to real infrastructure

Resource Metadata

Stores resource dependencies and attributes

Performance Data

Caches resource attributes for faster operations

Backend Configuration

Backends define where Terraform's state is stored. While the default is local, production environments should use remote backends.

Remote Backend Example (AWS S3) 
terraform {
  backend "s3" {
    bucket = "my-terraform-state-bucket"
    key    = "path/to/my/terraform.tfstate"
    region = "us-east-1"
  }
}

State Locking

State locking prevents multiple users from running Terraform simultaneously on the same state file, which could lead to conflicts and data loss.

Important

Always use state locking in team environments to prevent concurrent modifications.

Modules & Reusability

What are Terraform Modules?

A Terraform module is a set of Terraform configuration files in a single directory. Even a simple configuration consisting of a single directory with one or more .tf files is a module.

Module Structure

Root Module

The primary configuration directory containing your main Terraform files

Child Modules

Reusable components called from the root module or other modules

Published Modules

Modules from the Terraform Registry or other sources

Calling a Module 
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"
  version = "3.0.0"

  name = "my-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["us-west-2a", "us-west-2b", "us-west-2c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  enable_vpn_gateway = true
}

Module Benefits

Reusability

Write once, use multiple times across projects

Abstraction

Hide complexity behind simple interfaces

Consistency

Ensure standards across your organization

Collaboration

Share and reuse modules across teams

Providers & Resources

Provider Configuration

Providers are configured with settings that determine how they interact with their respective APIs. This often includes authentication details and regional configuration.

Multiple Provider Configuration 
# Configure the AWS Provider
provider "aws" {
  region = "us-east-1"
  profile = "production"
}

# Configure the Azure Provider
provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
  client_id       = var.client_id
  client_secret   = var.client_secret
  tenant_id       = var.tenant_id
}

Resource Dependencies

Terraform automatically handles most dependencies between resources, but you can also define explicit dependencies using the depends_on argument.

Explicit Dependencies 
resource "aws_vpc" "example" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_internet_gateway" "example" {
  vpc_id = aws_vpc.example.id
}

resource "aws_subnet" "example" {
  vpc_id            = aws_vpc.example.id
  cidr_block        = "10.0.1.0/24"
  availability_zone = "us-east-1a"

  # Explicit dependency
  depends_on = [aws_internet_gateway.example]
}

Data Sources

Data sources fetch information from providers that can be used elsewhere in your configuration.

Using Data Sources 
# Get the default VPC
data "aws_vpc" "default" {
  default = true
}

# Use the VPC ID from the data source
resource "aws_security_group" "example" {
  name        = "example"
  description = "Example security group"
  vpc_id      = data.aws_vpc.default.id

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Best Practices

1. Code Organization

Use a Standard Directory Structure

project/
├── main.tf          # Primary resources
├── variables.tf     # Input variables
├── outputs.tf       # Output values
├── terraform.tfvars # Variable values
└── modules/         # Reusable modules
    ├── network/
    ├── compute/
    └── database/

2. State Management

Use Remote State

Store state in a shared, secure location like S3, Azure Storage, or GCS

Enable State Locking

Prevent concurrent modifications with DynamoDB, Azure Blob Storage, etc.

Secure State Files

Encrypt state files and limit access with proper IAM policies

3. Security

Secrets Management

Never store secrets in plain text. Use environment variables, secret stores, or Terraform Cloud/Enterprise.

Least Privilege

Grant only the minimum permissions required for Terraform to manage resources.

Regular Auditing

Regularly review and audit your Terraform configurations and state files.

Pro Tip

Use terraform fmt to automatically format your configuration files according to Terraform language style conventions.

Advanced Concepts

1. Workspaces

Terraform workspaces allow you to maintain multiple states for a single configuration, enabling you to manage different environments (dev, staging, prod) with the same code.

Workspace Commands 
# List workspaces
terraform workspace list

# Create new workspace
terraform workspace new staging

# Select workspace
terraform workspace select production

2. Dynamic Blocks

Dynamic blocks allow you to dynamically construct repeatable nested blocks within resources, which is useful when the number of similar configuration blocks may vary.

Dynamic Block Example 
resource "aws_security_group" "example" {
  name = "example"

  dynamic "ingress" {
    for_each = var.ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}

3. Provisioners

Provisioners allow you to execute scripts on a local or remote machine as part of resource creation and destruction.

Note

Provisioners should be used as a last resort. Prefer native provider functionality or dedicated configuration management tools when possible.

4. Importing Existing Infrastructure

Terraform can import existing infrastructure into your state file, allowing you to manage resources that weren't originally created by Terraform.

Import Command 
terraform import aws_instance.web i-12345678
