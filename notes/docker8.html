Dockerfile – The Image Blueprint

Instructions for building Docker images 20 Slides

A Dockerfile is a text document that contains all the commands a user could call on the command line to assemble an image. It's the blueprint for creating Docker images.

Instructions

Each line is an instruction that creates a layer. Common instructions: FROM, RUN, COPY, CMD.

📝 Declarative syntax

Layers

Each instruction creates a new layer. Layers are cached for faster builds.

🧅 Stackable layers

Reusable

Dockerfiles are version-controlled, shareable, and can be used in CI/CD pipelines.

🔄 Infrastructure as Code
Analogy: A Dockerfile is like a recipe. The image is the dish you cook from it.
Built with docker build Filename: Dockerfile (no extension)

FROM – The Base Image

Every Dockerfile starts with FROM

FROM sets the base image for your build. All other instructions build on top of this.

# Basic FROM
FROM ubuntu:22.04

# FROM with alias (multi-stage)
FROM golang:1.19 AS builder

# FROM scratch (empty image)
FROM scratch

Best Practices

  • Use official images when possible
  • Specify specific tags (not latest)
  • Use Alpine for smaller images
  • Use multi-stage for build/runtime separation

Common Mistakes

  • Using latest tag (unstable)
  • Choosing overly large base images
  • Not using multi-stage for compiled languages

RUN – Executing Commands

Build-time commands

RUN executes commands during the build process, creating a new layer.

# Shell form (runs in /bin/sh)
RUN apt-get update && apt-get install -y python3

# Exec form (JSON array)
RUN ["apt-get", "update"]

# Combine commands to reduce layers
RUN apt-get update && \
  apt-get install -y curl && \
  rm -rf /var/lib/apt/lists/*
Tip: Combine RUN commands to reduce the number of layers and keep images small.

COPY vs ADD – Adding Files

Copying files into the image

COPY

Recommended – simple file/directory copying.

COPY index.html /app/
COPY ./src/ /app/src/
COPY --from=builder /app/bin /app/
📁 Simple and predictable

ADD

Extended version – supports URLs and auto-extract archives.

ADD https://example.com/file.tar.gz /tmp/
ADD archive.tar.gz /app/
📦 More features, less predictable
Recommendation: Use COPY unless you need URL support or auto-extraction. COPY is more transparent.

WORKDIR – Setting Working Directory

Context for subsequent commands

WORKDIR sets the working directory for all subsequent instructions (RUN, CMD, COPY, etc.).

# Sets working directory
WORKDIR /app

# Can be relative to previous WORKDIR
WORKDIR /app
WORKDIR src
# Final path: /app/src

# Creates directory if it doesn't exist
WORKDIR /var/www/html

Best Practice

Always set WORKDIR early in your Dockerfile. It makes paths consistent and predictable.

Equivalent

WORKDIR /app is equivalent to RUN mkdir -p /app && cd /app.

ENV – Environment Variables

Setting configuration

ENV sets environment variables that persist in the container.

# Set a single variable
ENV NODE_ENV production

# Set multiple variables
ENV DB_HOST=localhost \
  DB_PORT=5432 \
  DB_USER=admin

Use Cases

  • Application configuration
  • Feature flags
  • Paths and directories
  • Build-time vs runtime variables

ARG vs ENV

ARG is build-time only. ENV persists in the container.

🔧 ARG for build, ENV for runtime

ARG – Build-Time Variables

Parameterizing builds

ARG defines variables that can be passed at build time.

# Define ARG with default value
ARG VERSION=1.0.0
ARG APP_ENV=production

# Use the ARG
ENV APP_VERSION=$VERSION
RUN echo "Building version $VERSION"

# Build with custom ARG
$ docker build --build-arg VERSION=2.0.0 -t myapp .
Tip: Use ARG for version numbers, build environments, and feature flags. Use ENV for runtime configuration.

USER – Changing User Context

Security best practice

USER sets the user to use when running the container and subsequent instructions.

# Create a user and switch to it
FROM ubuntu:22.04
RUN groupadd -r appgroup && useradd -r -g appgroup appuser
USER appuser

# Switch to user by UID
USER 1000:1000

Best Practices

  • Create a non-root user
  • Set USER before CMD
  • Use least privilege principle

Why It Matters

Running as root is a security risk. If a container is compromised, the attacker gets root access.

EXPOSE – Documentation

Informing users about ports

EXPOSE informs users which ports the container listens on. It's documentation, not publishing.

# Single port
EXPOSE 80

# Multiple ports
EXPOSE 80 443

# TCP/UDP
EXPOSE 8080/tcp
EXPOSE 53/udp
Important: EXPOSE does NOT publish the port. It's metadata. Ports are published with docker run -p.

View Exposed Ports

$ docker inspect --format='{{.Config.ExposedPorts}}' image

CMD vs ENTRYPOINT – Running the Container

Defining the default command

CMD

Defines the default command. Can be overridden by docker run arguments.

CMD ["nginx", "-g", "daemon off;"]
CMD echo "Hello World"
📝 Default executable

ENTRYPOINT

Defines the executable. Arguments are appended to it.

ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
🎯 Fixed executable
Combined: ENTRYPOINT sets the executable, CMD provides default arguments.

HEALTHCHECK – Container Health

Monitoring container liveness

HEALTHCHECK tells Docker how to test if a container is working.

# Basic healthcheck
HEALTHCHECK CMD curl -f http://localhost/ || exit 1

# With options
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost/ || exit 1

Options

  • --interval: Check frequency (default 30s)
  • --timeout: Command timeout (default 30s)
  • --retries: Fail after N failures (default 3)
  • --start-period: Grace period for startup

States

  • starting: Initial startup phase
  • healthy: Container is working
  • unhealthy: Failed health checks

VOLUME – Persistent Data

Declaring mount points

VOLUME creates a mount point for persistent data.

# Single volume
VOLUME /var/lib/mysql

# Multiple volumes
VOLUME ["/data", "/var/log", "/config"]

# Named volume (not in Dockerfile, use docker run)
# docker run -v mydata:/data image
Best Practice: Use VOLUME in Dockerfile for directories that should be persisted. Use docker run -v or --mount to create volumes at runtime.

Multi-Stage Builds – Optimizing Images

Build and runtime separation

Multi-stage builds use multiple FROM statements to separate build environment from runtime.

# Build stage
FROM golang:1.19 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp .

# Runtime stage (much smaller)
FROM alpine:latest
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]

Benefits

  • Smaller final images
  • No build tools in runtime
  • Better security
  • Faster deployments

Example

Go app: ~800MB with build tools → ~10MB with only binary.

Secrets in Dockerfiles (BuildKit)

Secure secret handling

BuildKit allows mounting secrets during build without embedding them in the image.

# Dockerfile with secret mount
FROM python:3.9
WORKDIR /app
RUN --mount=type=secret,id=github_token \
  export TOKEN=$(cat /run/secrets/github_token) && \
  pip install --extra-index-url https://$TOKEN@private.pypi.com/ mypackage

# Build with secret
$ DOCKER_BUILDKIT=1 docker build \
  --secret id=github_token,src=./token.txt -t myapp .
Security: Secrets are never stored in the image layers, protecting sensitive data.

Layer Caching – Build Optimization

Speed up builds with cache

Docker caches layers. Unchanged layers are reused.

# Efficient – dependencies first, code last
FROM node:18-alpine
WORKDIR /app
# Copy package files first (changes less often)
COPY package*.json ./
RUN npm install # Cached unless package.json changes
# Copy source code last (changes often)
COPY . .
CMD ["npm", "start"]

Cache Best Practices

  • Order from least to most frequently changing
  • Combine RUN commands
  • Use --cache-from for external cache
  • Use BuildKit for better caching

Cache Invalidation

Any change breaks cache for that layer and all subsequent layers.

SHELL – Changing the Default Shell

Customizing command execution

SHELL allows you to change the default shell used for shell-form commands.

# Use bash instead of sh
SHELL ["/bin/bash", "-c"]
RUN echo "Hello from bash"

# Use PowerShell on Windows
SHELL ["powershell", "-Command"]
Note: The default shell is /bin/sh on Linux. Change it if you need bash-specific features.

.dockerignore – Exclude Files

Keep build context clean

.dockerignore excludes files from the build context, speeding up builds and preventing secrets from being included.

# Example .dockerignore
node_modules/
.git/
.env
*.log
Dockerfile
.dockerignore
README.md
tests/
coverage/

Benefits

  • Faster builds
  • Smaller build context
  • Prevents secrets in image
  • Reduces network transfer

Common Mistakes

  • Forgetting to ignore node_modules
  • Not ignoring .env files
  • Ignoring too much (e.g., *.js)

Building with Dockerfile

The docker build command
# Basic build
$ docker build -t myapp:latest .

# Build with specific Dockerfile
$ docker build -f Dockerfile.prod -t myapp:prod .

# Build with BuildKit (modern builder)
$ DOCKER_BUILDKIT=1 docker build -t myapp .

# Build with cache from previous image
$ docker build --cache-from myapp:latest -t myapp:new .

Common Flags

  • -t / --tag: Name and tag
  • -f / --file: Custom Dockerfile path
  • --build-arg: Pass build-time variables
  • --no-cache: Ignore cache

Context

The . at the end is the build context. Everything in this directory is sent to the daemon.
