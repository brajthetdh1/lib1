Q1

01.What is Docker, and how does it differ from a virtual machine?

Docker is a platform for developing, shipping, and running applications in lightweight containers.

Container
  • Shares host OS kernel
  • Lightweight (MBs)
  • Starts in seconds
  • Less overhead
Virtual Machine
  • Has full OS with kernel
  • Heavy (GBs)
  • Starts in minutes
  • More overhead
Docker uses namespaces & cgroups for isolation; VMs use hypervisors.
Q2

02.What is a Docker image?

A Docker image is a lightweight, standalone, executable package that includes everything needed to run a piece of software:

  • Code
  • Runtime
  • System tools
  • Libraries
  • Settings

Images are read-only and composed of layers. They serve as templates for creating containers.

Analogy: An image is like a class in programming; a container is an instance.
Q3

03.What is a Docker container?

A Docker container is a running instance of a Docker image. It adds a writable layer on top of the image layers.

Containers are:

  • Isolated – have their own filesystem, network, and process space
  • Ephemeral – designed to be stopped, started, and destroyed easily
  • Lightweight – share the host kernel
docker run nginx creates and starts a container from the nginx image.

Q6

06.What is a Dockerfile?

A Dockerfile is a text file containing instructions to build a Docker image.

# Example Dockerfile
FROM ubuntu:22.04
WORKDIR /app
COPY . .
RUN make
CMD ["./myapp"]
  • FROM – base image
  • RUN – execute commands during build
  • COPY – copy files from host
  • CMD – command to run when container starts

Q8

08.What is a Hypervisor?

A hypervisor is software that creates and runs virtual machines (VMs). It allows multiple OSes to run on a single host.

Type 1 (Bare Metal)
  • Runs directly on hardware
  • Examples: VMware ESXi, KVM
Type 2 (Hosted)
  • Runs on top of OS
  • Examples: VirtualBox, VMware Workstation

Docker does NOT use a hypervisor – it uses the host kernel directly.

Q30

30.What is a multi-stage build?

Multi-stage builds use multiple FROM statements to separate build environment from runtime environment.

# Build stage
FROM golang:1.19 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp

# Runtime stage (smaller)
FROM alpine:latest
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]

Benefits: Smaller images, no build tools in runtime, better security.

31.How do you reduce Docker image size?

RUN apt-get update && \

Q32

32.What is Build Cache in Docker?

Build Cache reuses layers from previous builds to speed up subsequent builds.

  • Each instruction creates a layer
  • If a layer hasn't changed, Docker reuses it from cache
  • A change in a layer invalidates that layer and all subsequent layers
# Order matters: dependencies first, code last
COPY package*.json ./ # Changes less often
RUN npm install # Cached if package.json unchanged
COPY . . # Changes often – invalidates only this layer

--no-cache ignores cache. --cache-from uses external cache.

Q34

34.What is the FROM scratch image?

scratch is a completely empty base image. It has no filesystem, no shell, nothing.

  • Used for static binaries (Go, C, Rust)
  • Smallest possible image size
  • No shell – cannot run docker exec or use shell commands
  • Minimal attack surface
FROM scratch
COPY myapp /myapp
CMD ["/myapp"]

Use case: Go applications compiled to static binaries.

Q35

35.What is the HEALTHCHECK instruction?

HEALTHCHECK tells Docker how to test if a container is working.

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost/ || exit 1
  • --interval – how often to check (default 30s)
  • --timeout – command timeout (default 30s)
  • --retries – failures before marking unhealthy (default 3)
  • --start-period – grace period for startup

States: starting, healthy, unhealthy.

Used by orchestration tools (Kubernetes, Swarm) for health checks.
Q36

36.What is the difference between EXPOSE and -p mapping?

EXPOSE (in Dockerfile)
  • Documentation only
  • Informs users which ports the container listens on
  • Does NOT publish the port
  • Used for metadata
-p (docker run)
  • Publishes the port to the host
  • Maps container port to host port
  • Makes container accessible from outside
  • Example: -p 8080:80
Q37

37.What is ARG in a Dockerfile?

ARG defines build-time variables that can be passed at build time.

# Define ARG with default
ARG VERSION=1.0.0
ARG APP_ENV=production

# Use the ARG
ENV APP_VERSION=$VERSION
RUN echo "Building version $VERSION"

# Build with custom ARG
docker build --build-arg VERSION=2.0.0 -t myapp .
  • ARG is build-time only
  • Does NOT persist in the final image
  • Use for version numbers, build environments
Q38

38.What is ENV in a Dockerfile?

ENV sets environment variables that persist in the container.

# Single variable
ENV NODE_ENV production

# Multiple variables
ENV DB_HOST=localhost \
  DB_PORT=5432
  • ENV persists in the container
  • Can be overridden at runtime with -e
  • Use for application configuration

vs ARG: ARG is build-time only; ENV persists in the container.

Q39

39.Why use Alpine Linux as a base image?

  • Very small: ~5 MB (vs Ubuntu ~77 MB)
  • Security-focused: minimal attack surface
  • Fast: faster pulls and builds
  • musl libc instead of glibc (smaller, but sometimes compatibility issues)
FROM alpine:3.18
RUN apk add --no-cache python3
Note: Alpine uses apk package manager, not apt.
Q40

40.What is the order of instructions in a Dockerfile for optimal caching?

Order instructions from least frequently changing to most frequently changing.

# 1. Base image (rarely changes)
FROM node:18-alpine

# 2. Work directory
WORKDIR /app

# 3. Dependencies (changes less often)
COPY package*.json ./
RUN npm install

# 4. Application code (changes most often)
COPY . .

# 5. Runtime configuration
EXPOSE 3000
CMD ["npm", "start"]

Why: Changes to code only invalidate the final layer, not the dependencies layer.

Q42

42.What is the default network driver?

The default network driver is bridge.

  • Creates a virtual bridge called docker0 on the host
  • Containers get IPs in the 172.17.0.0/16 range
  • Containers can communicate on the same bridge
  • Uses NAT (iptables) for external access
# Check default bridge
ip link show docker0
Q43

43.How do containers on the same network communicate?

  • Containers on the same user-defined bridge network can communicate by service name (DNS resolution)
  • On the default bridge network, they can only communicate by IP address
  • They can also use --link (legacy) for DNS
# Create network
docker network create mynet

# Run containers on same network
docker run -d --net mynet --name web nginx
docker run -it --net mynet alpine ping web # Works by name
User-defined networks provide automatic DNS-based service discovery.

# List networks

Q46

46.What is the difference between bridge and host network modes?

bridge
  • Container has its own network stack
  • Uses docker0 bridge
  • IP: 172.17.0.x
  • Isolated from host
  • NAT for external access
  • Default
host

47.What is overlay networking?

Overlay networks enable multi-host container communication using VXLAN tunneling.

  • Connects containers across multiple hosts
  • Used in Swarm and Kubernetes
  • Encapsulates traffic between hosts
  • Supports encryption (IPsec)
  • Requires a key-value store (or Swarm control plane)
# Create overlay network (Swarm)
docker network create --driver overlay myoverlay

Q51

51.What is the --link option in Docker?

--link is a legacy option for container communication, predating user-defined networks.

docker run -d --name db postgres
docker run -d --link db:db --name web nginx
  • Adds DNS entry for the linked container
  • Adds environment variables with connection info
  • Legacy – use user-defined networks instead

Q52

52.What are Docker volumes and why are they used?

Docker volumes are persistent storage mechanisms that survive container deletion.

  • Stored in /var/lib/docker/volumes/
  • Managed by Docker (not the container)
  • Can be shared between containers
  • Decouple data from container lifecycle
  • Support volume drivers (NFS, cloud storage)
# Create and use a volume
docker volume create mydata
docker run -v mydata:/app/data nginx
Use when: Persistent data, sharing between containers, backups.
Q53

53.What is the difference between a volume and a bind mount?

Volume
  • Managed by Docker
  • Stored in /var/lib/docker/volumes/
  • Portable across hosts
  • Can use volume drivers
  • Recommended for production
Bind Mount
  • Managed by the user
  • Any path on the host
  • Host-dependent
  • Bypasses Docker's storage
  • Good for development
Q54

54.How do you create and use a volume?

# Create a volume
docker volume create mydata

# List volumes
docker volume ls

# Run with volume
docker run -v mydata:/app/data nginx

# Using --mount (explicit)
docker run --mount source=mydata,target=/app/data nginx

# Inspect volume
docker volume inspect mydata

You can also use anonymous volumes (-v /app/data) but named volumes are easier to manage.

Q55

55.Will data be lost when a container exits?

  • Writable layer: Data is lost when container is removed
  • Volumes: Data persists even after container is removed
  • Bind mounts: Data persists on the host
  • tmpfs mounts: Data is lost when container stops (in-memory)
Best practice: Use volumes for persistent data, not the writable layer.
Q56

56.How do you backup Docker volume data?

Use a temporary container to backup/restore volume data:

# Backup volume to tar
docker run --rm -v mydata:/data -v $(pwd):/backup alpine \
  tar czf /backup/mydata-backup.tar.gz -C /data .

# Restore from tar
docker run --rm -v mydata:/data -v $(pwd):/backup alpine \
  tar xzf /backup/mydata-backup.tar.gz -C /data
  • The temporary container mounts the volume and a host directory
  • Uses tar to create/restore the backup
  • Can also use rsync or other tools
Q57

57.When should you use bind mounts?

Bind mounts are best for:

  • Development – hot-reload code changes
  • Mounting configuration files from host
  • Sharing host directories with containers
  • Accessing host filesystem from container
# Development: mount source code
docker run -v $(pwd):/app -w /app node npm start

# Mount config file
docker run -v /host/nginx.conf:/etc/nginx/nginx.conf:ro nginx
Not recommended for production due to host dependency.
Q58

58.How do you secure Docker containers?

  • Run as non-root user (USER in Dockerfile, --user in run)
  • Drop capabilities (--cap-drop=ALL --cap-add=NET_BIND_SERVICE)
  • Use minimal base images (Alpine, scratch)
  • Scan images for vulnerabilities
  • Use seccomp profiles to restrict syscalls
  • Use AppArmor or SELinux for MAC
  • Enable user namespace remapping (userns-remap)
  • Set resource limits (memory, CPU)
  • Use secrets instead of environment variables for sensitive data
  • Keep images updated and patched
  • Use HTTPS/TLS for registry communication
Q59

59.Why should you not run containers as root?

  • Security risk: If container is compromised, attacker gets root on the host
  • Root in container = root on host (if namespaces are escaped)
  • Can modify host filesystem, install packages, access sensitive data
  • Principle of least privilege: Only grant necessary permissions
# In Dockerfile
RUN useradd -m -u 1000 appuser
USER appuser
CMD ["/app/myapp"]

# At runtime
docker run --user 1000:1000 myapp
Even if you run as non-root, still use capabilities and seccomp.
Q60

60.How do you limit container resources?

# CPU limits
docker run --cpus=1.5 nginx
docker run --cpu-shares=512 nginx

# Memory limits
docker run --memory=512m nginx
docker run --memory-swap=1g nginx

# Combined
docker run --cpus=2 --memory=1g nginx

Why: Prevents "noisy neighbor" issues – one container consuming all host resources.

Best practice: Always set memory and CPU limits in production.

Q62

62.What are Docker secrets?

Docker secrets are a way to manage sensitive data (passwords, API keys, TLS certificates) in Docker Swarm.

  • Encrypted in transit and at rest
  • Stored in the Swarm manager
  • Mounted as files in containers (/run/secrets/)
  • Not stored in images or environment variables
  • Only accessible to services that need them
# Create a secret
echo "password123" | docker secret create db_password -

# Use secret in service
docker service create --secret db_password --name web nginx
Q63

63.What is the difference between secrets and environment variables for sensitive data?

Environment Variables
  • Plain text
  • Visible in docker inspect
  • Visible in process list
  • Not encrypted
  • Easy to leak
  • Not recommended for secrets
Secrets
  • Encrypted
  • Not visible in inspect
  • Mounted as files
  • Encrypted at rest
  • Audited
  • Recommended for production
Q64

64.What is the principle of least privilege in Docker?

The principle of least privilege means granting only the minimum permissions necessary for a container to function.

  • User: Run as non-root (USER, --user)
  • Capabilities: Drop all, add only needed (--cap-drop=ALL --cap-add=NET_BIND_SERVICE)
  • Resources: Set memory and CPU limits
  • Security profiles: Use seccomp, AppArmor, SELinux
  • Network: Use isolated networks, limit exposure
  • Filesystem: Use read-only root filesystem (--read-only)
  • Secrets: Use Docker secrets, not environment variables
Q65

65.What is Docker Compose and how does it work?

Docker Compose is a tool for defining and running multi-container applications.

  • Uses a docker-compose.yml file
  • Defines services, networks, volumes
  • Single command: docker-compose up
  • Automatically creates networks
  • Handles dependencies

How it works:

  1. Parses the Compose file
  2. Creates networks and volumes
  3. Pulls/builds images
  4. Creates and starts containers
docker-compose up -d starts everything in the background.

68.What is depends_on in Compose?

depends_on defines service startup dependencies.

services:
  web:
    depends_on:
      - db
      - redis
  • Ensures start order (db and redis start before web)
  • Does NOT wait for the service to be ready
  • Use health checks or wait-for-it scripts for readiness
  • Consider condition: service_healthy in newer versions
depends_on only ensures containers are running, not that the application is ready.

Q71

71.What is Docker Swarm?

Docker Swarm is Docker's native clustering and orchestration solution.

  • Groups multiple Docker hosts into a cluster
  • Uses manager nodes and worker nodes
  • Manager nodes use Raft consensus for state
  • Deploys services with replicas
  • Built into Docker Engine (no separate installation)
  • Supports rolling updates, load balancing, failover
Swarm is simpler than Kubernetes but less feature-rich.
Q72

72.How do you initialize a Swarm cluster?

# Initialize Swarm on manager node
docker swarm init

# With specific advertise address
docker swarm init --advertise-addr 192.168.1.10

# Check swarm status
docker info | grep Swarm

# List nodes
docker node ls

After initialization, you'll get a join token for worker and manager nodes.

Q73

73.How do you add worker nodes to Swarm?

# On manager, get join token
docker swarm join-token worker

# On worker node, join the swarm
docker swarm join --token SWMTKN-xxx 192.168.1.10:2377

# Add manager nodes
docker swarm join --token SWMTKN-yyy --manager 192.168.1.10:2377
  • Tokens are secret – keep them safe
  • Manager tokens allow adding more managers (Raft quorum)
  • Worker tokens allow adding worker nodes
  • Use docker node ls to verify nodes are joined
Q74

74.What is a Docker service in Swarm?

A Docker service is the definition of a task to be run on Swarm nodes.

  • Specifies the image to use
  • Number of replicas
  • Ports to publish
  • Networks to connect to
  • Update strategy (rolling updates)
  • Resource limits
# Create a service
docker service create --name web --replicas 3 -p 8080:80 nginx

Tasks: Each running instance of a service is a task.

Q75

75.How do you deploy a service with replicas?

# Deploy service with replicas
docker service create --name web --replicas 5 -p 8080:80 nginx

# List services
docker service ls

# List tasks
docker service ps web

# With resource limits
docker service create --name web --replicas 3 \
  --limit-memory 512m --limit-cpu 0.5 \
  -p 8080:80 nginx

Swarm automatically distributes tasks across available worker nodes.

Q76

76.How do you scale a Swarm service?

# Scale up/down
docker service scale web=10

# Update with new replicas
docker service update --replicas 8 web

# Autoscaling is not built-in
# Use external tools like Docker Swarm Metrics
  • Scale up when load increases
  • Scale down when load decreases
  • Swarm automatically manages task distribution
  • Node failures: tasks are re-scheduled to healthy nodes
Swarm does NOT have built-in autoscaling. Use third-party tools or Kubernetes.

Q78

78.What is high availability in Docker Swarm?

High availability in Swarm means the system continues to function even when nodes fail.

  • Manager nodes: Raft consensus (odd number, minimum 3 for HA)
  • Worker nodes: Tasks are re-scheduled to healthy nodes
  • Service replication: Multiple replicas across different nodes
  • Rolling updates: Update without downtime
  • Health checks: Unhealthy tasks are replaced
Recommendation: 3 manager nodes, 2+ worker nodes for production.
Q79

79.A container exits immediately after starting — how do you debug?

  • Check logs: docker logs container
  • Run interactively: docker run -it image /bin/bash (or entrypoint)
  • Override CMD: docker run -it --entrypoint /bin/bash image
  • Check Dockerfile: Verify CMD/ENTRYPOINT, WORKDIR, permissions

    80.Container works locally but fails in production — why?

    • Environment variables: Production variables may differ
    • Resource limits: Production may have lower CPU/memory

    Q85

    85.You updated a Dockerfile but container still uses old code — why?

    91.What are Docker namespaces and cgroups?

    Q92

    92.What are Docker layers and how do they work?

    Docker layers are the building blocks of images.

    • Each instruction in a Dockerfile creates a layer
    • Layers are stacked using Union File System (OverlayFS)
    • Layers are read-only
    • Container adds a writable layer on top
    • Copy-on-write (CoW): Files are copied to the writable layer only when modified
    # View layer history
    docker history nginx

    Benefits: Smaller storage, faster pulls, efficient caching.

    Q93

    93.What is the difference between an image and a layer?

    Image
    • Complete stack of layers
    • Has a manifest and config
    • Can be tagged and pushed
    • Immutable
    • Example: nginx:latest
    Layer
    • Single filesystem delta
    • Contains changes from previous layer
    • Has a digest (SHA256)
    • Can be shared between images
    • Example: RUN apt-get update creates a layer
    Q94

    94.What is "copy-on-write" (COW) in Docker?

    Copy-on-write (CoW) is an optimization where files are only copied when they are modified.

    • Container's writable layer is initially empty
    • When a file is read: it's read from the image layer
    • When a file is modified: it's copied to the writable layer first
    • Future reads read from the writable layer
    • Image layers remain immutable
    COW makes containers lightweight and fast to start.

    Q98

    98.When should Docker NOT be used?

    • High-performance computing: Bare metal is faster
    • GUI applications: Requires special setup (X11 forwarding)
    • Full OS simulation: Need VM for different kernel
    • Windows apps on Linux: Windows containers need Windows host

    • Very small deployments: Overhead may not be worth it
    Use VMs when you need full OS isolation. Use bare metal for extreme performance.

    Q100

    100.How does Docker differ from Podman?

    Docker
    • Client-server architecture
    • Daemon (dockerd) runs as root
    • Requires root privileges (by default)
    • Single daemon manages all containers
    • More mature, larger ecosystem
    Podman
    • Daemonless architecture
    • Containers run as fork/exec
    • Can run rootless by default
    • More secure out of the box
    • OCI-compliant, compatible with Docker CLI

    Key difference: Podman is daemonless and rootless by default, making it more secure. Docker is more mature with a larger ecosystem.

    Both use the same OCI image format and can run the same containers.
