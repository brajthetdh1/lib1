Control Groups (Cgroups) – The Resource Governors

Linux kernel feature for resource limiting 20 Slides

Cgroups (Control Groups) are a Linux kernel feature that limits, accounts for, and isolates the resource usage (CPU, memory, disk I/O, network) of a collection of processes.

Resource Limiting

Set hard limits on CPU, memory, disk I/O, and network bandwidth that a container can consume.

📊 Prevent resource exhaustion

Prioritization

Control relative resource sharing between containers (CPU shares, I/O weight).

⚖️ Fair scheduling

Accounting

Monitor and report resource usage for billing, monitoring, and debugging.

📈 Observability
Key Insight: While namespaces provide isolation, cgroups provide resource control. They work together to make containers possible.
Cgroups v2 is the modern implementation (since kernel 4.15) Docker uses cgroups to enforce --memory, --cpus flags

Cgroups Evolution – v1 vs v2

Understanding the two versions

Cgroups v1

Legacy version – separate hierarchies per resource type (CPU, memory, devices, etc.).

  • Multiple filesystem mounts
  • Each controller has its own tree
  • Complex and less efficient
📁 /sys/fs/cgroup/{cpu,memory,...}

Cgroups v2

Unified hierarchy – single filesystem with all controllers in one tree.

  • Single mount point
  • Better resource management
  • PSI (Pressure Stall Information)
  • Improved performance
📁 /sys/fs/cgroup/ (unified)
# Check which version is active
$ mount | grep cgroup
cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime)
Docker supports both, but cgroups v2 is recommended for modern kernels

CPU Cgroups – Limiting CPU Usage

Control CPU time and cores

CPU Shares

Relative CPU weight (default 1024). Higher value = more CPU time under contention.

$ docker run --cpu-shares=512 nginx
⚖️ Proportional sharing

CPU Cores (CPUs)

Restrict to specific CPU cores (e.g., only use CPU 0 and 1).

$ docker run --cpuset-cpus=0,1 nginx
🎯 Core pinning

CPU Quota

Hard CPU limit as a percentage of total cores. --cpus=2 = 2 full cores.

$ docker run --cpus=1.5 nginx # 1.5 CPU cores max
📊 Exact control

Memory Cgroups – Controlling RAM & Swap

Prevent memory exhaustion

Memory Limit

Hard limit on memory usage. OOM killer triggers when exceeded.

$ docker run --memory=512m nginx
💾 512 MB max

Swap Limit

Control swap usage. --memory-swap sets total (memory + swap).

$ docker run --memory=512m --memory-swap=1g nginx
🔄 512MB RAM + 512MB swap
OOM Killer: When a container exceeds memory limit, the kernel's Out-Of-Memory killer terminates processes to free up memory.
# Check memory cgroup for a container
$ cat /sys/fs/cgroup/memory/docker/<container-id>/memory.limit_in_bytes
536870912 # 512 MB

Disk I/O Cgroups – Storage Control

Manage storage performance

I/O Weight

Relative priority for disk access (range 10-1000). Higher = more I/O.

$ docker run --blkio-weight=500 nginx
⚖️ Proportional I/O

I/O Rate Limits

Hard limits on read/write operations per second (IOPS) and bandwidth.

$ docker run --device-read-bps /dev/sda:10mb nginx
📊 10 MB/s read limit

Available Options

  • --blkio-weight – relative weight
  • --device-read-bps – bytes per second (read)
  • --device-write-bps – bytes per second (write)
  • --device-read-iops – IOPS (read)
  • --device-write-iops – IOPS (write)

Network Cgroups – Bandwidth Control

Manage network throughput

Network cgroups limit network bandwidth at the container level using the net_cls and net_prio controllers.

Bandwidth Limits

Set outbound/inbound bandwidth limits using tc (traffic control).

# Requires net_cls controller
$ docker run --net=bridge nginx
🚦 Traffic shaping

Network Priority

Set network priority for outbound traffic (net_prio controller).

# net_prio.ifpriomap
eth0 5
🎯 QoS control
Note: Network cgroups are less commonly used directly in Docker. Most network control is done via network drivers and CNI plugins.

Cgroup Subsystems – All Controllers

Complete list of cgroup controllers
cpu – CPU time
memory – RAM & swap
blkio – Disk I/O
net_cls – Network classification
net_prio – Network priority
pids – Process count
cpuacct – CPU accounting
devices – Device access
freezer – Suspend/resume
Docker uses cpu, memory, blkio, devices, pids, and freezer primarily

Inspecting Cgroups in Docker

How to view cgroup settings

docker inspect

View cgroup settings applied to a container.

$ docker inspect --format '{{.HostConfig.Memory}}' container
536870912

Cgroup Filesystem

Directly inspect cgroup files for a container.

# Get container PID
$ docker inspect --format '{{.State.Pid}}' container
12345

# View cgroup limits
$ cat /proc/12345/cgroup
# All cgroup limits for a container
$ docker stats --no-stream container
CONTAINER CPU % MEM USAGE / LIMIT MEM % NET I/O BLOCK I/O
web 0.05% 256MiB / 512MiB 50.0% 1.2MB 2.3MB

How Docker Applies Cgroups

From docker run to cgroup files
1 User runs docker run --memory=512m --cpus=2 nginx
2 dockerd parses flags and creates container config
3 runc writes cgroup values to /sys/fs/cgroup/
4 Kernel enforces limits on container processes
✅ Container runs with resource constraints
# Cgroup path for a container
/sys/fs/cgroup/memory/docker/<container-id>/
/sys/fs/cgroup/cpu/docker/<container-id>/

Cgroup Flags Reference

All Docker cgroup-related flags
--cpus – CPU core limit (e.g., 1.5)
--cpu-shares – CPU relative weight (1024 default)
--cpuset-cpus – Specific CPU cores (e.g., 0-3)
--memory – RAM limit (e.g., 512m, 2g)
--memory-swap – Total memory+swap limit
--blkio-weight – I/O priority (10-1000)
--device-read-bps – Read bytes/sec limit
--device-write-bps – Write bytes/sec limit

Cgroup Subsystems in Detail

Deep dive into each controller

cpu + cpuacct

cpu: Limit CPU time with shares and quotas.
cpuacct: Report CPU usage statistics.

📊 cpu.stat, cpu.max

memory

Limit RAM, swap, and kernel memory. Reports usage and OOM events.

💾 memory.limit_in_bytes, memory.usage_in_bytes

blkio

Control I/O access to block devices. Weight, throttling, and statistics.

📁 blkio.weight, blkio.throttle.read_bps_device

pids

Limit the number of processes inside the container.

📊 pids.max, pids.current

Practical Example – CPU Limits

Running with CPU constraints
# Run container with 1.5 CPU cores limit
$ docker run -d --name stress --cpus=1.5 --cpu-shares=512 stress --cpu 4

# Verify CPU limit
$ docker inspect --format '{{.HostConfig.CpuQuota}}' stress
150000 # 1.5 cores (150% of 100ms period)

# Check with docker stats
$ docker stats stress --no-stream
CONTAINER CPU % MEM USAGE / LIMIT
stress 149.8% 2.3MiB / 2GiB
Tip: Use --cpus for simple limits, --cpu-shares for proportional sharing in multi-container environments.

Practical Example – Memory Limits

Running with memory constraints
# Run container with 256MB RAM and 512MB swap
$ docker run -d --name memory-test --memory=256m --memory-swap=512m nginx

# Check memory limits
$ docker inspect --format '{{.HostConfig.Memory}}' memory-test
268435456

# View memory cgroup stats
$ docker exec memory-test cat /sys/fs/cgroup/memory/memory.limit_in_bytes
268435456

OOM Behavior

If a container exceeds --memory, the kernel kills the container process. Use --oom-kill-disable to prevent OOM killing (not recommended).

Practical Example – Disk I/O Limits

Controlling storage performance
# Limit read speed to 10MB/s on /dev/sda
$ docker run -d --name io-test \
  --device-read-bps /dev/sda:10mb \
  --device-write-bps /dev/sda:5mb \
  ubuntu dd if=/dev/zero of=/tmp/test bs=1M count=100

Read Limit

--device-read-bps – bytes per second
--device-read-iops – IOPS (operations per second)

Write Limit

--device-write-bps – bytes per second
--device-write-iops – IOPS

These limits apply to specific block devices, not filesystems

Cgroups in Docker Compose

Defining resource limits in compose
version: '3'
services:
  web:
    image: nginx
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: "512M"
        reservations:
          cpus: "0.5"
          memory: "256M"
Limits – maximum resources the container can use.
Reservations – guaranteed minimum resources.

Cgroups & Security – Preventing DoS

Protecting the host and other containers

Protection

✅ Prevents a single container from consuming all host resources

✅ Ensures fair resource distribution

✅ Isolates resource exhaustion attacks

Risks

⚠️ Misconfigured limits can cause OOM kills

⚠️ --memory-swap=-1 allows unlimited swap

⚠️ Container can still consume network bandwidth

Best Practice: Always set memory and CPU limits in production to prevent noisy neighbors.

Cgroups v2 – The New Standard

Benefits of the unified hierarchy

Advantages

  • Single, unified hierarchy
  • PSI (Pressure Stall Information)
  • Better resource control (e.g., memory.reclaim)
  • Improved performance for container runtimes
  • Consistent interface across controllers

Migration

  • Kernel 4.15+ (or 5.x+ for full support)
  • Docker 20.10+ supports v2
  • Check with docker info | grep "Cgroup Version"
🐧 Modern systems use cgroups v2
# Check cgroup version
$ docker info | grep "Cgroup Version"
Cgroup Version: 2

Troubleshooting Cgroups

Common issues and solutions

OOM Kills

Issue: Container is killed due to memory limit
Solution: Increase --memory or reduce application memory usage

💡 Check docker logs for OOM messages

CPU Throttling

Issue: Application is CPU-limited
Solution: Increase --cpus or --cpu-shares

💡 Use docker stats to verify limits

Debug Commands

# Check cgroup mount
$ mount | grep cgroup
# View container cgroup path
$ docker inspect --format '{{.State.Pid}}' container
$ cat /proc/<pid>/cgroup
