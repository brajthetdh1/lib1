Docker Architecture

A 10 000‑word deep dive into the engine, kernel, and ecosystem 15 min read

Part I: The Macro‑Architecture – Trinity of Client, Daemon, Registry

At its highest conceptual level, Docker is a three‑legged stool. Understanding the rigid separation of duties in this trinity is the first step to mastering the system.

Docker Client

The stateless CLI/UI that marshals requests to the daemon. Reads ~/.docker/config.json, speaks REST API, and supports TLS for remote hosts.

Docker Daemon (dockerd)

Persistent background process that manages images, containers, networks, and volumes. Uses a modular plugin system and maintains state in /var/lib/docker.

Docker Registry

Stateless, horizontally‑scalable artifact server. Implements Registry API V2 with content‑addressable storage (CAS) and layer deduplication.

Client ↔ Daemon: The client translates docker run into HTTP POST requests to the Unix socket /var/run/docker.sock (or a TCP endpoint). Daemon ↔ Registry: The daemon pulls/pushes images using manifest digests, verifying layer integrity with SHA256 hashes.

Part II: The Kernel Primitives – Namespaces, Cgroups, OverlayFS

Containers are just processes on the host kernel. Docker orchestrates five Linux namespaces, cgroups, and OverlayFS to build the illusion of isolation.

Namespaces (Isolation)

  • PID – process tree isolation; container sees its process as PID 1.
  • NET – network stack isolation; each container gets its own eth0 via veth pairs.
  • MNT – mount point isolation; root filesystem is constructed from image layers.
  • UTS – hostname & domain isolation.
  • User – UID mapping; container root (0) can be mapped to a non‑privileged host UID (e.g., 100000).

Control Groups (cgroups)

Resource governors. The daemon writes CPU, memory, and I/O limits to /sys/fs/cgroup. The kernel enforces these limits and triggers OOM kills when memory exceeds.

Union File Systems (OverlayFS)

Copy‑on‑write (CoW) storage. Overlay2 uses lowerdir (image layers), upperdir (container writable layer), and merged (unified view). Writing a file triggers a copy‑up operation, preserving immutability of images.

Netfilter & iptables: Docker inserts DNAT rules into the DOCKER chain for port publishing. This kernel‑level packet processing is extremely fast and avoids user‑space proxy overhead.

Part III: The Runtime Stack – containerd, runc, and the Shim

The modern Docker runtime is layered for resilience and OCI compliance.

containerd

Core container lifecycle manager. Handles image pulls, snapshotting, and container state. Exposes a gRPC API and delegates process execution to runc.

runc

OCI‑compliant low‑level runtime. Reads config.json, invokes libcontainer to create namespaces and cgroups, then starts the container process.

containerd‑shim

Survives containerd restarts. Reaps zombie processes, manages TTY, and enables live‑restore. The shim is the parent of the container process.

Flow: dockerd → gRPC → containerd → containerd-shim → runc → kernel.
If the daemon crashes, the shim keeps containers running; when the daemon restarts, it re‑attaches to the shim.

Part IV: Image Architecture – Layers, Content Addressing, BuildKit

Docker images are Merkle‑tree‑style layer stacks. Each instruction in a Dockerfile (e.g., RUN, COPY) creates a new layer.

# Example Dockerfile layers
FROM ubuntu:20.04 # layer 1
RUN apt-get update && apt-get install -y nginx # layer 2
COPY ./index.html /var/www/html/ # layer 3

BuildKit

The modern builder (replacing the legacy sequential builder). Uses a Low‑Level Build (LLB) graph to enable parallel execution of independent steps. Supports cache mounts (e.g., --mount=type=cache,target=/root/.m2) and secret mounting without embedding secrets in the final image.

Content Addressing & Registry V2

Each layer is identified by a SHA256 digest. The manifest lists these digests, ensuring integrity. The daemon performs dynamic chunk size negotiation during pulls for optimal throughput.

Part V: Networking – Drivers, CNI, and DNS

Docker’s networking is powered by libnetwork and the Container Network Model (CNM).

Network Drivers

  • Bridge – default; uses docker0 bridge and NAT via iptables.
  • Host – no isolation; container shares host network stack (maximum performance).
  • Overlay – VXLAN encapsulation for multi‑host communication; encrypted with IPsec.
  • Macvlan / Ipvlan – assign a MAC address; direct physical network integration.
  • None – no networking; fully isolated.

IPAM & Embedded DNS

The IPAM driver allocates subnets dynamically. The embedded DNS (127.0.0.11) resolves service names to container IPs, enabling round‑robin load balancing. This is fundamental for service discovery.

CNI integration: In Kubernetes mode, Docker delegates networking to CNI plugins (Calico, Flannel). The daemon uses the same containerd runtime to serve both standalone and K8s workloads.

Part VI: Storage – Volumes, Bind Mounts, and Plugins

Docker provides three primary ways to manage persistent data:

  • Volumes – managed by Docker, stored in /var/lib/docker/volumes/. Survive container deletion. Support volume drivers (NFS, EBS, etc.).
  • Bind Mounts – mount a host directory directly; bypasses the Union File System.
  • tmpfs – in‑memory mounts; lost on stop (used for secrets and caches).

Storage Driver (Overlay2)

Overlay2 uses four directories: lowerdir (image layers), upperdir (container writable layer), workdir (atomic operations), and merged (final view). Copy‑up operations are expensive for large files, so databases often use bind mounts or volumes.

Part VII: Security Architecture – Defense in Depth

Security is woven into every layer of the stack.

  • User Namespace Remapping – container root maps to a non‑privileged host UID (e.g., 100000).
  • Seccomp Profiles – default profile blocks ~44 dangerous syscalls (reboot, mount, etc.).
  • AppArmor / SELinux – mandatory access control (MAC) profiles limit file and network access.
  • Capabilities – drops CAP_SYS_ADMIN, keeps only essential ones (e.g., CAP_NET_BIND_SERVICE).
  • Rootless Mode – daemon and containers run without root privileges, using slirp4netns for networking.
  • Content Trust (Notary) – signs images with TUF framework; client verifies signatures before pulling.

Part VIII: Observability – Logging, Metrics, Tracing

Logging Drivers

STDOUT/STDERR from containers is captured by the daemon and sent to a pluggable driver: json‑file (default), syslog, fluentd, awslogs, splunk, etc. The architecture decouples log storage from the container.

Metrics & Prometheus

The /containers/{id}/stats endpoint streams real‑time CPU, memory, network, and block I/O metrics (derived from cgroups). Prometheus can scrape this endpoint for monitoring and alerting.

Distributed Tracing

The daemon can emit OpenTelemetry spans via --otel flags, enabling tracing of API requests across the client‑daemon‑registry stack.

Part IX: Orchestration – Swarm & Kubernetes

Docker Swarm Mode

Swarm adds Raft consensus, manager/worker nodes, services, and tasks. The ingress network (routing mesh) uses an overlay network to route traffic to the correct worker via a Virtual IP (VIP).

Docker & Kubernetes

Docker can serve as the container runtime for Kubernetes via the CRI (Container Runtime Interface). In this architecture, kubelet talks directly to containerd, bypassing dockerd—a clean separation that highlights the modularity of the stack.

Part X: Lifecycle Walkthrough – docker run in Detail

A step‑by‑step journey of a docker run -d -p 8080:80 nginx command:

  1. Client → Daemon: CLI builds a JSON payload and POSTs to /containers/create over the Unix socket.
  2. Image Resolution: Daemon checks local cache; if missing, it pulls the manifest and layers from the registry using content‑addressable digests.
  3. Container Config: Daemon allocates an IP via IPAM, creates OverlayFS snapshot (new upperdir), and writes host config.
  4. Daemon → containerd: gRPC call passes OCI spec and rootfs path.
  5. containerd → runc: containerd-shim invokes runc create and runc start.
  6. Kernel: runc creates namespaces, sets cgroups, executes pivot_root, and execves the ENTRYPOINT.
  7. Supervision: The shim monitors the process; STDOUT is captured and sent to the logging driver.
  8. Cleanup: On docker stop, SIGTERM then SIGKILL; iptables rules are removed, IP is released, and the upperdir is optionally deleted.
Live Restore: If dockerd crashes, the shim keeps containers alive. When the daemon restarts, it rescans containerd’s state and re‑attaches.

Part XI: Edge Cases & Failure Modes

  • OOM Kill: Exceeding memory limits triggers kernel OOM killer; shim reports exited (137).
  • Network Partition (Swarm): Manager loses quorum → read‑only mode; workers continue running existing tasks.
  • Disk Full: Daemon pauses writes to containers; exposes disk pressure via metrics.

Part XII: The Future – WebAssembly, Rootless, and Beyond

Docker’s architecture is evolving to support WebAssembly (Wasm) modules alongside OCI containers. containerd can now invoke a Wasm runtime (e.g., Wasmtime) using the same docker run interface. The registry stores .wasm artifacts just like images.

With the deprecation of Swarm, Docker is focusing on being the best developer‑friendly runtime for Kubernetes, ensuring that dockerd works seamlessly with CRI.

Conclusion: The Symphony of the Kernel

Docker’s architecture is a masterful orchestration of user‑space and kernel‑space primitives. It leverages namespaces, cgroups, and OverlayFS to deliver near‑VM isolation with near‑bare‑metal performance. The modular layering—Client, Daemon, containerd, runc, and shim—ensures resilience, security, and portability.

Understanding this architecture is not just about knowing how docker run works; it is about grasping the future of cloud‑native computing. Docker has redefined how we package, distribute, and execute software at scale, and its architecture remains a blueprint for modern infrastructure.
