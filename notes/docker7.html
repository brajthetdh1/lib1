Docker Images – The Foundation

Read-only templates for containers 30 Slides

A Docker image is a lightweight, standalone, executable package that includes everything needed to run a piece of software: code, runtime, system tools, libraries, and settings.

Immutable

Images are read-only. Once built, they never change. Any modifications go to the container's writable layer.

📦 Immutable artifacts

Layered

Images are composed of layers. Each instruction in a Dockerfile creates a new layer.

🧅 Union File System

Portable

Images can be shared via registries (Docker Hub, private registries) and run anywhere Docker runs.

🚀 Build once, run anywhere
Analogy: An image is like a class in programming. A container is an instance of that class.
Built from a Dockerfile Stored in registries

Image Layers – The Building Blocks

Each instruction creates a layer

Every command in a Dockerfile creates a new layer. Layers are stacked on top of each other.

Layer 4 CMD ["nginx", "-g", "daemon off;"] – Container startup command
Layer 3 COPY ./site /usr/share/nginx/html – Application code
Layer 2 RUN apt-get update && apt-get install -y nginx – Dependencies
Layer 1 FROM ubuntu:22.04 – Base image
Layer Reuse: If you build the same image multiple times, unchanged layers are reused from cache.

Dockerfile – The Image Blueprint

Instructions for building images

A Dockerfile is a text file containing instructions that define how to build an image.

# Example Dockerfile for a Node.js app
FROM node:18-alpine # Base image
WORKDIR /app # Set working directory
COPY package*.json ./ # Copy package files
RUN npm install # Install dependencies
COPY . . # Copy application code
EXPOSE 3000 # Document port
CMD ["npm", "start"] # Default command

FROM

Sets the base image. All images start from a base.

COPY / ADD

Copies files from host to image.

RUN / CMD

RUN – executes during build. CMD – executes when container starts.

Image Naming & Tagging

Identifying images

Images are identified by repository and tag.

# Full image name format
[registry/][namespace/]repository:tag

# Examples
nginx:latest # Official image, latest tag
ubuntu:22.04 # Specific version
myapp:v1.2.3 # Custom tag
docker.io/library/nginx:1.21 # Full registry path

Tags

Tags are like version numbers. latest is the default tag.

🏷️ Version control

Digests

Images also have a digest (SHA256 hash) for immutable identification.

🔐 Content-addressable

Image Registries – Distribution

Storing and sharing images

Docker Hub

The default public registry. Contains official images and community images.

🌐 docker.io

Private Registries

Host your own registry (e.g., Amazon ECR, Google Container Registry, Azure ACR, or self-hosted).

Building Images – docker build

The build process

The docker build command builds an image from a Dockerfile and context.

# Basic build
$ docker build -t myapp:latest .

# Build with specific Dockerfile
$ docker build -f Dockerfile.prod -t myapp:prod .

# Build with BuildKit (modern builder)
$ DOCKER_BUILDKIT=1 docker build -t myapp .
BuildKit: The modern builder with parallel execution, cache mounts, and secret handling.

Layer Caching – Speed Up Builds

Build faster with cache

Docker caches layers. If a layer hasn't changed, Docker reuses it, skipping re-execution.

# Efficient Dockerfile – order matters!
FROM node:18-alpine
WORKDIR /app
# COPY package files first – cache dependencies
COPY package*.json ./
RUN npm install # Cached unless package.json changes
# Copy source code last
COPY . .
CMD ["npm", "start"]

Cache Benefits

✅ Faster builds
✅ Less bandwidth
✅ Efficient CI/CD

Cache Invalidation

⚠️ Any change breaks cache for that layer and all subsequent layers
💡 Order layers from least to most frequently changing

Multi-Stage Builds – Optimize Images

Separate build and runtime environments

Multi-stage builds allow you to use multiple FROM statements in one Dockerfile, reducing final image size.

# Build stage
FROM golang:1.19 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp .

# Runtime stage (much smaller)
FROM alpine:latest
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]
Result: Final image contains only the binary (~10MB) instead of full Go toolchain (~500MB).

.dockerignore – Exclude Unnecessary Files

Keep build context small

The .dockerignore file excludes files and directories from the build context, speeding up builds and keeping images smaller.

# Example .dockerignore

.git/
.env
*.log
Dockerfile
.dockerignore
README.md
tests/
Benefit: Prevents sending large files (like node_modules) to the Docker daemon, and avoids accidentally embedding secrets.

Image Digests – Immutable Identification

Content-addressable storage

Every image has a digest – a SHA256 hash of the image manifest. This provides immutable identification.

# Get image digest
$ docker images --digests
REPOSITORY TAG DIGEST
nginx latest sha256:abc123...

# Pull by digest (ensures exact image)
$ docker pull nginx@sha256:abc123...

# Inspect digest
$ docker inspect nginx --format='{{.RepoDigests}}'
Security: Using digests ensures you get exactly the image you expect, protecting against tag tampering.

Image Pull & Push – Registry Operations

Moving images

Pulling

Download images from a registry.

$ docker pull nginx:latest
$ docker pull alpine:3.18
📥 Layers are downloaded in parallel

Pushing

Upload images to a registry.

$ docker tag myapp user/myapp:v1
$ docker push user/myapp:v1
📤 Only uploads missing layers
Tip: Use docker pull --platform linux/amd64 to pull a specific architecture.

Copying Images Between Registries

Migrate images

Tag and push images to move them between registries.

# Pull from source registry
$ docker pull source-registry.com/myapp:v1

# Tag for destination
$ docker tag source-registry.com/myapp:v1 dest-registry.com/myapp:v1

# Push to destination
$ docker push dest-registry.com/myapp:v1

Cross-Cloud Migration

Move images between AWS ECR, GCR, ACR, Docker Hub, and self-hosted registries.

Registry Sync

Use docker pull + docker push for manual sync, or tools like skopeo for advanced migration.

Removing Images – Clean Up

Free up disk space
# Remove specific image
$ docker rmi myapp:v1
$ docker rmi abc123def456 # Remove by image ID

# Remove all unused images
$ docker image prune

# Remove all unused images (force)
$ docker image prune -a -f

# Remove all images
$ docker rmi -f $(docker images -q)
Warning: Removing images in use by containers will fail. Use -f to force removal.

Base Images – The Starting Point

Choosing the right foundation

Ubuntu

Full-featured Linux distribution. Large but familiar.

📦 ~77 MB

Alpine

Minimal, security-focused. Uses musl libc. Very small.

📦 ~5 MB

Scratch

Empty image. For static binaries. Minimal attack surface.

📦 0 MB
Tip: Use scratch for Go/static binaries. Use alpine for most applications. Use ubuntu when you need full compatibility.

Image Security – Best Practices

Secure your images

Do's

  • Use official/base images from trusted sources
  • Run as non-root user
  • Keep images up to date
  • Scan for vulnerabilities (docker scan)
  • Use minimal base images

Don'ts

  • Don't embed secrets
  • Don't use latest tag in production
  • Don't run as root
  • Don't use outdated base images

USER appuser
CMD ["/app/myapp"]

Saving & Loading Images – Offline Transfer

Move images without a registry

Save

Export image(s) to a tar file.

$ docker save -o myapp.tar myapp:latest
$ docker save myapp:latest > myapp.tar
📦 Single file

Load

Import image(s) from a tar file.

$ docker load -i myapp.tar
$ docker load < myapp.tar
📥 Restore images
Use Case: Transfer images between air-gapped environments or when no registry is available.

Exporting vs Saving – Differences

Two export methods

docker save

Preserves: Image layers, metadata, tags, and history.

Output: Tar file with layers and manifest.

Use: Backing up or transferring images.

📦 Full image backup

docker export

Preserves: Only the container filesystem (flattened).

Output: Tar file of container's filesystem.

Use: Inspecting filesystem, not for image distribution.

📁 Filesystem snapshot
# Export container filesystem (flattened)
$ docker export container1 > container1.tar

# Import as image (loses history)
$ docker import container1.tar myapp:flat

Multi-Architecture Images – Manifest Lists

Support multiple CPU architectures

Images can support multiple architectures using manifest lists (fat manifests).

# Official images support multiple architectures
$ docker manifest inspect nginx:latest

# Build multi-arch image
$ docker buildx build --platform linux/amd64,linux/arm64,linux/arm/v7 \
  -t user/myapp:latest --push .

Supported Platforms

  • linux/amd64 (x86_64)
  • linux/arm64 (ARM64)
  • linux/arm/v7 (ARM32)
  • linux/ppc64le
  • linux/s390x

Tools

  • docker buildx – Modern builder
  • docker manifest – Manage manifests
  • QEMU for emulation

BuildKit – The Modern Builder

Next-generation build engine

BuildKit replaces the legacy builder with advanced features.

Features

  • Parallel execution of independent stages
  • Cache mounts (persistent across builds)
  • Secrets mounting (without embedding)
  • Skip unused stages
  • Better cache invalidation

Usage

# Enable BuildKit
$ DOCKER_BUILDKIT=1 docker build -t myapp .

# Use cache mount
RUN --mount=type=cache,target=/root/.m2 mvn package

Secrets in Builds – BuildKit

Secure secret handling

BuildKit allows mounting secrets during build without embedding them in the image.

# Dockerfile with secret mount
FROM python:3.9
WORKDIR /app
RUN --mount=type=secret,id=github_token \
  export GITHUB_TOKEN=$(cat /run/secrets/github_token) && \
  pip install --extra-index-url https://$GITHUB_TOKEN@private.pypi.com/ mypackage

# Build with secret
$ DOCKER_BUILDKIT=1 docker build \
  --secret id=github_token,src=./token.txt \
  -t myapp .
Security: Secrets are never stored in the image layers, protecting sensitive data.

Image Rollback – Revert to Previous Versions

Deploying older versions

Docker images are immutable, making rollback simple – just run an older tag.

# Deploy specific version
$ docker run -d myapp:v1.2.3

# Rollback to previous version
$ docker stop myapp-container
$ docker run -d myapp:v1.2.2 # Previous version

Best Practices

  • Tag images with semantic versions
  • Keep previous versions available
  • Use docker images to list available versions

CI/CD Integration

Tag every build with commit hash or build number for easy rollback.

Image Customization – Dockerfile Patterns

Common Dockerfile patterns

Python

FROM python:3.9-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Java

FROM openjdk:11-jre-slim
WORKDIR /app
COPY target/app.jar app.jar
CMD ["java", "-jar", "app.jar"]

Go (Multi-stage)

FROM golang:1.19 AS builder
WORKDIR /app
COPY . .
RUN go build -o app
FROM alpine
COPY --from=builder /app/app /app
CMD ["/app"]

Node.js

FROM node:18-alpine
WORKDIR /app
COPY package*.json .
RUN npm ci --only=production
COPY . .
CMD ["node", "server.js"]

Image Export Formats – OCI vs Docker

Standard image formats

Docker Format

The original Docker image format. Used by default in Docker.

  • Manifest v2 schema
  • Widely supported
  • Backward compatible
📦 Legacy but standard

OCI Format

Open Container Initiative standard. Used by containerd, CR-O, and modern tools.

  • OCI image spec
  • More flexible
  • Future-proof
📦 Industry standard
# Build OCI-compliant image
$ docker build --oci -t myapp:latest .

# Convert to OCI layout
$ docker buildx build --output type=oci,dest=myapp.oci.tar .

Image Signing & Content Trust

Verify image authenticity

Docker Content Trust (DCT) allows publishers to sign images using TUF (The Update Framework) via Notary.

# Enable content trust
$ export DOCKER_CONTENT_TRUST=1

# Push signed image
$ docker push user/myapp:latest
Signing and pushing trust metadata...

# Pull only signed images
$ docker pull user/myapp:latest
✓ Signed by: user@example.com
Benefits: Prevent tampering, ensure authenticity, and enable audit trails for image deployment.
