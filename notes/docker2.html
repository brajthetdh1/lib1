Linux Namespaces – The Isolation Wall

Kernel primitives that make containers possible 6 namespaces

Namespaces wrap global system resources — like process IDs, network interfaces, and user IDs — in an abstraction that makes each container think it has its own dedicated OS.

PID

Process ID isolation. The container sees its main process as PID 1, while the host sees a high-numbered PID.

🔒 prevents host process visibility

NET

Network stack isolation. Each container gets its own eth0, IP address, routing tables, and iptables.

🌐 veth pairs + bridge

MNT

Mount point isolation. The container root filesystem is assembled from image layers via OverlayFS.

📂 copy‑on‑write

UTS

Hostname & domain name isolation. A container can set its hostname without affecting the host.

🏷️ hostname web-01

User

UID/GID mapping. Container root (UID 0) can be mapped to a non‑privileged host UID (e.g., 100000).

🛡️ privilege escalation protection

IPC

Inter‑process communication isolation. Prevents containers from accessing each other’s shared memory or message queues.

🚫 System V / POSIX isolation

PID Namespace – Process Tree Isolation

Each container gets its own process hierarchy

Inside the container the main process is PID 1 (like an init system). Outside, the kernel maps it to a random high PID (e.g., 23456) on the host.

# On the host
$ ps aux | grep nginx
root 23456 0.0 0.1 ... nginx: master

# Inside the container
$ docker exec web ps aux
root 1 0.0 0.1 ... nginx: master

Security benefit: a compromised container cannot see or signal host processes.

Why it matters

Each container can run its own systemd or init without conflicts. The kernel handles the PID translation transparently.

NET Namespace – Network Isolation

Full network stack per container veth pairs + iptables

Virtual Ethernet (veth)

Docker creates a pair of virtual interfaces: one in the container (eth0), the other attached to the host bridge (docker0).

iptables & NAT

The daemon inserts DNAT rules to forward host ports to container IPs. This enables -p 8080:80.

# Host network bridge
$ ip link show docker0
3: docker0: <BROADCAST,MULTICAST,UP> mtu 1500
# Container sees its own eth0
$ docker exec web ip addr
15: eth0@if16: <BROADCAST,MULTICAST,UP> inet 172.17.0.2/16

Overlay networks use VXLAN to extend NET namespaces across hosts.

MNT Namespace – Mount Isolation

Root filesystem from image layers

OverlayFS combines lowerdir (image layers) and upperdir (writable layer) into a single merged view. Each container has its own mount namespace.

# Container root filesystem
$ docker exec web ls /
bin dev etc home lib proc root sys tmp usr var

# Host mounts are invisible inside the container
$ docker exec web mount
overlay on / type overlay (rw,relatime,...)

Security & Performance

Mount namespace prevents containers from accessing host filesystems. Copy‑on‑write (CoW) makes starting containers fast and disk‑efficient.

User Namespace – UID Mapping

The strongest security isolation

Mapping

Container UID 0 (root) is mapped to a non‑privileged host UID, e.g., 100000. Even if a container is compromised, the attacker only has user‑level privileges on the host.

Configuration

Enable with dockerd --userns-remap=default. All files written to volumes are owned by the remapped UID.

# Inside container – root
$ docker exec web whoami
root

# On the host – the process is owned by UID 100000
$ ps -eo uid,pid,cmd | grep nginx
100000 23456 nginx: master
Rootless mode takes this further: the entire daemon runs without root privileges.

IPC & UTS Namespaces

Hostname & inter‑process communication

UTS (Hostname)

Each container can set its own hostname using --hostname. The host’s hostname remains untouched.

$ docker run --hostname web-01 alpine hostname
web-01

IPC (Inter‑Process Communication)

Isolates System V semaphores, shared memory, and POSIX message queues. Prevents containers from interfering with each other’s IPC resources.

🧩 separate /dev/shm
Together with PID, NET, MNT, and User, these six namespaces form the complete isolation boundary.

How Docker Orchestrates Namespaces

From docker run to kernel
1 dockerd receives API request
2 containerd prepares OCI spec
3 runc reads config.json and creates namespaces
4 Kernel instantiates PID, NET, MNT, UTS, User, IPC
✅ Container process starts inside the namespaces
# Check namespaces of a running container
$ ls -l /proc/$(docker inspect -f '{{.State.Pid}}' web)/ns/
ipc → ipc:[4026532441]
net → net:[4026532477]
pid → pid:[4026532456]
user → user:[4026532361]
uts → uts:[4026532442]

Each namespace type has a unique inode number — proof of isolation.

Security & Best Practices

Hardening namespace usage
  • Enable user namespace remapping — maps container root to a non‑privileged host UID.
  • Drop capabilities — avoid CAP_SYS_ADMIN which can allow namespace manipulation.
  • Use non‑default networks — user‑defined bridge networks provide automatic DNS and better isolation.
  • Seccomp / AppArmor — restrict syscalls even within the namespace.
Namespaces are the foundation, but security requires layers (cgroups, capabilities, seccomp).
