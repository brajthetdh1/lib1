Mounting in Docker – Overview

Data persistence & sharing 3 main types

By default, data written inside a container is ephemeral. When the container is removed, all its data is lost. Docker provides mounts to persist data, share files between containers, and access host files.

Volumes

Managed entirely by Docker. Stored in /var/lib/docker/volumes/. Survive container deletion.

✅ Recommended for production

Bind Mounts

Mount a host directory directly into the container. Bypasses the Union File System.

⚡ Fast for development

tmpfs Mounts

In‑memory filesystem. Data is lost on container stop. Perfect for caches and secrets.

🔐 No disk persistence
Volumes are the preferred way for persistent data docker volume create + --mount

Volumes – The Preferred Way

Managed by Docker, decoupled from the container

Create & Use

docker volume create mydata

docker run -v mydata:/app/data nginx

📦 Named volumes

Lifecycle

Volumes survive container removal. They are only deleted when you run docker volume rm or docker system prune.

♻️ Persistent storage
# Create a volume
$ docker volume create postgres-data

# Run a container with the volume
$ docker run -d \
  --name postgres \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:13
Why volumes? They are more portable, secure, and easier to back up than bind mounts. Volume drivers also support remote storage (NFS, AWS EBS, etc.).

Bind Mounts – Host Access

Mount a host directory into the container Development & testing

Bind mounts map a host path (absolute or relative) to a container path. Changes are immediately visible on both sides.

# Mount current directory to /app in container
$ docker run -v $(pwd):/app -w /app node npm start

# Using --mount syntax (more explicit)
$ docker run --mount type=bind,src=/host/data,dst=/container/data alpine

Pros

✅ Great for development – edit code on host, see changes instantly in container.

✅ Access host configuration files.

Cons

⚠️ Host filesystem dependency – less portable.

⚠️ Permissions issues (UID/GID mismatches).

⚠️ Not ideal for production.

Use :ro to make bind mounts read‑only: -v /host:/container:ro

tmpfs Mounts – In‑Memory Storage

Ephemeral, fast, and secure

tmpfs mounts store data only in the host's memory (RAM). Nothing is written to disk.

# Mount tmpfs to /tmp inside container
$ docker run --tmpfs /tmp:rw,size=512m alpine

# Using --mount syntax
$ docker run --mount type=tmpfs,dst=/cache,tmpfs-size=256m nginx

Use Cases

🔹 Temporary caches

🔹 Session data

🔹 Secrets that should never hit disk

🔹 High‑performance scratch space

Limitations

⚠️ Data is lost on container stop/restart

⚠️ Limited by host RAM

⚠️ Not suitable for persistent data

Security: tmpfs is ideal for storing sensitive tokens or credentials that should never be persisted to disk.

Mount Syntax – -v vs --mount

Two ways to mount data

-v or --volume

Older, shorter syntax

# Volume
-v myvol:/app
# Bind mount
-v /host:/container
# tmpfs
--tmpfs /tmp
⚡ Quick & simple

--mount

Newer, explicit, recommended

# Volume
--mount type=volume,src=myvol,dst=/app
# Bind mount
--mount type=bind,src=/host,dst=/container
# tmpfs
--mount type=tmpfs,dst=/tmp,tmpfs-size=512m
📖 More readable & feature‑rich
Tip: Use --mount in scripts and production for clarity. Use -v for quick local testing.

Mount Propagation – Sharing Mounts

How mounts appear in nested containers

When you mount a volume into a container, you can control how that mount is propagated to sub‑mounts inside the container (or to other containers).

shared

Mounts propagate from the host to the container and back to the host. Changes in the container are visible on the host.

slave

Mounts propagate from the host to the container, but not back from container to host.

private

No propagation in either direction. The container's mount is completely isolated.

# Set propagation with --mount
$ docker run --mount type=bind,src=/host,dst=/container,bind-propagation=shared alpine
Default propagation is rslave on Linux

Managing Volumes – CLI Commands

Full lifecycle control

Inspect & List

$ docker volume ls
$ docker volume inspect myvol

Remove

$ docker volume rm myvol
$ docker volume prune # remove unused

Backup & Restore

# Backup volume to tar
$ docker run --rm -v myvol:/data -v $(pwd):/backup alpine \
  tar czf /backup/myvol-backup.tar.gz -C /data .

# Restore from tar
$ docker run --rm -v myvol:/data -v $(pwd):/backup alpine \
  tar xzf /backup/myvol-backup.tar.gz -C /data
💾 Volume backup using a temporary container

Volume Drivers – External Storage

Plugins for cloud & network storage

Docker volumes can be backed by volume drivers (plugins) that provide access to remote storage systems.

AWS EBS

docker volume create --driver=aws

☁️ Elastic Block Storage

NFS

docker volume create --driver=local --opt type=nfs

📂 Network File System

Azure File

docker volume create --driver=azurefile

☁️ Azure Files
# Create volume with NFS driver
$ docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.100,rw \
  --opt device=:/exports/data \
  nfs-data
CSI integration: Docker supports the Container Storage Interface (CSI) for advanced volume plugins.

Decision guide
