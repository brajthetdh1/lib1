Java Base Images – Choosing the Right One

OpenJDK, Eclipse Temurin, Amazon Corretto

Eclipse Temurin

Open-source JDK from the Eclipse Foundation. Community-supported.

FROM eclipse-temurin:17-jre-alpine
📦 Recommended

Amazon Corretto

Amazon's no-cost, multi-platform distribution. Long-term support.

FROM amazoncorretto:17-alpine
☁️ AWS-friendly

OpenJDK

Official OpenJDK images. Deprecated in favor of Temurin.

FROM openjdk:17-jdk-slim
⚠️ Legacy
Tip: Always use -jre variants for smaller images. Use -alpine for smallest footprint.

Image Size Comparison

  • Full JDK: ~500-800MB
  • JRE slim: ~200-300MB
  • JRE alpine: ~150-200MB
  • Alpine + JRE: ~80-120MB

Version Compatibility

  • Java 8: eclipse-temurin:8
  • Java 11: eclipse-temurin:11
  • Java 17: eclipse-temurin:17
  • Java 21: eclipse-temurin:21

Simple Java Dockerfile

Basic structure
# Basic Java Dockerfile
FROM eclipse-temurin:17-jre-alpine

WORKDIR /app
COPY target/myapp.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
  • 1 Use a JRE base image (not JDK)
  • 2 Set working directory to /app
  • 3 Copy the built JAR file
  • 4 EXPOSE the application port
  • 5 Define the CMD to run the JAR
    • Build & Run:
    $ docker build -t myapp .
    $ docker run -p 8080:8080 myapp

    JVM Options in Docker

    Optimizing Java in containers
    # Passing JVM options
    CMD ["java", "-Xmx512m", "-Xms256m", "-jar", "app.jar"]

    # Using environment variables
    ENV JAVA_OPTS="-Xmx512m -Xms256m"
    CMD ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

    Important JVM Flags

    • -Xmx – Max heap size
    • -Xms – Initial heap size
    • -XX:+UseContainerSupport – JVM sees container limits (Java 10+)
    • -XX:MaxRAMPercentage – Heap as % of container memory

    Java 8 vs 10+

    • Java 8: Manually set heap
    • Java 10+: JVM auto-detects container limits
    • Java 8u191+: -XX:+UseContainerSupport available

    Memory Tuning for Java in Containers

    Avoiding OOM kills
    # Using MaxRAMPercentage (Java 10+)
    CMD ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]

    # With container memory limit of 1GB
    $ docker run --memory=1g -e JAVA_OPTS="-XX:MaxRAMPercentage=70.0" myapp

    Recommended Settings

    • -XX:MaxRAMPercentage=70.0 (70% of container memory)
    • -XX:InitialRAMPercentage=50.0
    • -XX:+UseG1GC – Good for container environments
    • Reserve 30% for OS, JVM overhead

    Common Pitfalls

    • Setting heap too high → OOM kill
    • Ignoring container memory limits
    • Using old JVM that doesn't support container detection
    Best Practice: Set --memory on container and use -XX:MaxRAMPercentage in JVM.

    CPU Tuning for Java in Containers

    Optimizing CPU usage
    # JVM sees container CPU limits (Java 10+)
    # No extra flags needed – auto-detects CPU count
    # But you can explicitly set:
    CMD ["java", "-XX:ActiveProcessorCount=4", "-jar", "app.jar"]

    JVM CPU Settings

    • JVM auto-detects CPU shares
    • Parallel GC threads = CPU cores
    • ForkJoin pool = CPU cores
    • Java 10+ detects cgroup limits

    Manual Override

    $ docker run --cpus=2 myapp
    # JVM automatically adjusts
    Note: Garbage Collector threads = number of CPUs. For small containers, use -XX:ParallelGCThreads=2 to limit GC overhead.

    Java 8 in Containers – Special Considerations

    Legacy Java 8 support
    # Java 8 needs explicit container support (8u191+)
    FROM eclipse-temurin:8-jre-alpine
    CMD ["java", "-XX:+UseContainerSupport", "-XX:MaxRAMPercentage=70.0", "-jar", "app.jar"]

    Java 8 Limitations

    • Pre-8u191: No container awareness
    • Must manually set -Xmx
    • Must set -XX:ParallelGCThreads
    • Default GC is Parallel GC (not G1)

    Java 8 Best Practices

    • Use 8u192 or later
    • Explicitly set -Xmx
    • Consider upgrading to Java 11+
    • Use -XX:+UseG1GC

    Garbage Collection in Containers

    Choosing the right GC

    G1GC (Recommended)

    • Adaptive, low pause times
    • Good for multi-core systems
    • Best for containers
    • -XX:+UseG1GC

    ZGC (Java 11+)

    • Ultra-low latency
    • Sub-millisecond pauses
    • Requires more memory
    • -XX:+UseZGC
    # GC options in Dockerfile
    ENV JAVA_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=200"
    CMD ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
    Recommendation: G1GC for most applications. ZGC for latency-sensitive, high-memory apps.

    JAR Packaging – Fat JAR vs Thin JAR

    Packaging strategies

    Fat JAR (Uber JAR)

    • All dependencies bundled
    • Single file to copy
    • Larger image size
    • Spring Boot default
    📦 Simple, but larger

    Thin JAR

    • Dependencies in separate layers
    • Better cache reuse
    • Smaller image size
    • Spring Boot layered JAR
    🧅 Better for Docker cache
    Tip: Spring Boot 2.3+ supports layered JARs for optimal Docker layer caching.

    Spring Boot Layered JARs

    Optimal Docker caching
    # Spring Boot plugin configuration (pom.xml)
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
        <layers>
          <enabled>true</enabled>
        </layers>
      </configuration>
    </plugin>
    # Dockerfile with layered JAR
    FROM eclipse-temurin:17-jre-alpine
    WORKDIR /app
    COPY target/*.jar app.jar
    # Extract layers
    RUN java -Djarmode=layertools -jar app.jar extract
    COPY --from=builder /app/dependencies/ ./
    COPY --from=builder /app/snapshot-dependencies/ ./
    COPY --from=builder /app/spring-boot-loader/ ./
    COPY --from=builder /app/application/ ./
    CMD ["java", "-jar", "app.jar"]
    Benefit: Dependencies layer is cached. Only application layer changes on code updates.

    Maven Dockerfile – Multi-Stage

    Build and runtime separation
    # Multi-stage Maven build
    # Build stage
    FROM maven:3.8-openjdk-17 AS builder
    WORKDIR /app
    COPY pom.xml .
    RUN mvn dependency:go-offline # Download dependencies
    COPY src ./src
    RUN mvn package -DskipTests

    # Runtime stage
    FROM eclipse-temurin:17-jre-alpine
    WORKDIR /app
    COPY --from=builder /app/target/*.jar app.jar
    CMD ["java", "-jar", "app.jar"]

    Benefits

    • ✅ No Maven in final image
    • ✅ Smaller image
    • ✅ Better security
    • ✅ Faster builds with caching

    Cache Optimization

    • dependency:go-offline caches dependencies
    • Copies pom.xml first for cache reuse

    Gradle Dockerfile – Multi-Stage

    Gradle build in container
    # Multi-stage Gradle build
    # Build stage
    FROM gradle:7.6-jdk17 AS builder
    WORKDIR /app
    COPY build.gradle settings.gradle .
    RUN gradle dependencies --no-daemon # Cache dependencies
    COPY src ./src
    RUN gradle build -x test --no-daemon

    # Runtime stage
    FROM eclipse-temurin:17-jre-alpine
    WORKDIR /app
    COPY --from=builder /app/build/libs/*.jar app.jar
    CMD ["java", "-jar", "app.jar"]
    Tip: Use Gradle's --no-daemon to avoid leaving processes running.

    Spring Boot Dockerfile – Complete Example

    Production-ready
    # Production Spring Boot Dockerfile
    FROM eclipse-temurin:17-jre-alpine AS builder
    WORKDIR /app
    COPY --chown=appuser:appuser target/*.jar app.jar
    RUN java -Djarmode=layertools -jar app.jar extract

    FROM eclipse-temurin:17-jre-alpine
    RUN addgroup -S appgroup && adduser -S appuser -G appgroup
    USER appuser
    WORKDIR /app
    COPY --from=builder --chown=appuser:appuser /app/dependencies/ ./
    COPY --from=builder --chown=appuser:appuser /app/spring-boot-loader/ ./
    COPY --from=builder --chown=appuser:appuser /app/snapshot-dependencies/ ./
    COPY --from=builder --chown=appuser:appuser /app/application/ ./
    EXPOSE 8080
    ENV JAVA_OPTS="-XX:MaxRAMPercentage=70.0 -XX:+UseG1GC"
    ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS org.springframework.boot.loader.JarLauncher"]
    Production Ready: Non-root user, layered JAR, optimized JVM settings.

    Performance Tuning – Summary

    Optimize Java in containers

    Do's

    • Use -XX:MaxRAMPercentage=70.0
    • Use G1GC or ZGC
    • Set container memory limits
    • Use Alpine base images
    • Enable layered JARs

    Don'ts

    • Don't set fixed heap in containers
    • Don't use latest base images
    • Don't run as root
    • Don't ignore memory limits
    Golden Rule: Test performance under load. Adjust heap and GC based on application behavior.

    Container vs JVM – Understanding the Overhead

    Performance comparison

    JVM in Container

    • JVM sees container limits (Java 10+)
    • GC threads = CPUs
    • Heap = % of container memory
    • ~5-10% overhead vs bare metal

    Recommendations

    • Reserve 20-30% for OS/JVM overhead
    • Set CPU limits carefully
    • Monitor GC and memory
    Fact: Java in containers can achieve near-bare-metal performance with proper tuning.
