Docker Containers – The Running Instances

Lightweight, portable execution environments 30 Slides

A Docker container is a lightweight, standalone, executable package that includes everything needed to run a piece of software. Containers are instances of Docker images that run as isolated processes on the host system.

Instance of an Image

Containers are created from images. An image is a blueprint; a container is the built structure.

📦 Image → Container

Isolated

Containers have their own filesystem, network, and process space. They are isolated from each other and the host.

🔒 Namespaces & cgroups

Ephemeral

Containers are designed to be ephemeral – they can be stopped, started, and destroyed easily.

🔄 Stateless by default
Analogy: An image is like a recipe. A container is the dish you make from it.
Created from images using docker run Leverages kernel namespaces and cgroups

Image vs Container – The Difference

Immutable template vs runtime instance

Image

  • Read-only template
  • Composed of layers
  • Cannot be modified
  • Stored in registry
  • Blueprint for containers
📦 Static artifact

Container

  • Read-write instance
  • Adds writable layer on top
  • Can be modified during runtime
  • Running or stopped
  • Instantiation of an image
⚡ Running process
# Create a container from an image
$ docker run -d --name my-container nginx:latest

# Image remains unchanged, container is running
$ docker images nginx
$ docker ps

Running Containers – docker run

The most important command

docker run creates and starts a container from an image.

# Basic run
$ docker run nginx:latest

# Run in detached mode (background)
$ docker run -d nginx:latest

# Run with interactive terminal
$ docker run -it ubuntu:22.04 /bin/bash

# Run with name and port mapping
$ docker run -d --name web -p 8080:80 nginx:latest

-d

Detached mode – runs container in background.

-it

Interactive + TTY – for interactive shells.

--name

Assign a custom name to the container.

Inspecting Containers – docker inspect

Deep dive into container details

docker inspect shows all configuration and state information about a container.

# Full inspection
$ docker inspect container-name

# Get specific fields using --format
$ docker inspect --format='{{.State.Status}}' container
running

$ docker inspect --format='{{.NetworkSettings.IPAddress}}' container

$ docker inspect --format='{{.Config.Image}}' container
nginx:latest

State

Status, PID, exit code, start time.

Network

IP address, ports, network settings.

Mounts

Volumes and bind mounts attached.

Container Lifecycle – States

Understanding container states
Created Container has been created but not started. Resources reserved.
Running Container is running. Process is executing.
Paused Container processes are frozen (SIGSTOP).
Exited Container has stopped. May have crashed or been stopped gracefully.
Deleted Container has been removed. All resources freed.
# Check container state
$ docker ps -a
CONTAINER ID STATUS
abc123 Up 2 hours
def456 Exited (0) 5 minutes ago
ghi789 Created
jkl012 Paused

Interacting with Containers

Get inside your containers

docker exec

Run commands inside a running container.

$ docker exec -it container bash
$ docker exec container ls -la
$ docker exec -w /app container node app.js
🖥️ Interactive shell

docker logs

View container logs (STDOUT/STDERR).

$ docker logs container
$ docker logs -f container # Follow
$ docker logs --tail 100 container
📝 Debugging
Note: docker exec runs new processes inside the container's namespaces. docker attach connects to the container's main process.

Container Filesystem – The Writable Layer

Understanding container storage

When a container is created, a writable layer is added on top of the image layers. All changes are written here.

Writable Layer All changes made during runtime (logs, temp files, modifications)
Layer 3 Application code (COPY)
Layer 2 Dependencies (RUN apt-get)
Layer 1 Base image (FROM)
Key Point: Changes in the writable layer are lost when the container is deleted unless you use volumes.

Container Storage – Volumes & Persistence

Making data survive container lifecycle

Volumes

Docker-managed storage. Survives container deletion. Recommended for production.

$ docker volume create mydata
$ docker run -v mydata:/app/data nginx

Bind Mounts

Host directory mounted into container. Changes reflected on host.

$ docker run -v /host/data:/container/data nginx

Container Data Persistence

  • Writable layer: Ephemeral – lost on deletion
  • Volumes: Persistent – survive container deletion
  • Bind mounts: Persistent – host-dependent

Container Networking – Communication

Connecting containers and the outside world

Bridge

Default network. Containers on same bridge can communicate.

🌐 docker0 bridge

Host

Container uses host's network stack. No isolation.

⚡ Maximum performance

Overlay

Multi-host networking for Swarm/Kubernetes.

☁️ VXLAN tunneling
# Create a custom network
$ docker network create mynet

# Run containers on the network
$ docker run -d --net mynet --name web nginx
$ docker run -it --net mynet alpine ping web

Port Publishing – Exposing Services

Making containers accessible

Publish container ports to the host using -p or --publish.

# Map container port 80 to host port 8080
$ docker run -d -p 8080:80 nginx

# Map to specific host IP
$ docker run -d -p 127.0.0.1:8080:80 nginx

# Map port range
$ docker run -d -p 8080-8085:80-85 nginx

# Random port mapping
$ docker run -d -P nginx # Random high port

Published Ports

docker ps shows published ports in the PORTS column.

📊 0.0.0.0:8080->80/tcp

EXPOSE vs -p

EXPOSE in Dockerfile is documentation only. -p actually publishes.

Container Resources – CPU & Memory Limits

Control resource consumption

CPU Limits

$ docker run --cpus=1.5 nginx
$ docker run --cpu-shares=512 nginx
$ docker run --cpuset-cpus=0,1 nginx

Memory Limits

$ docker run --memory=512m nginx
$ docker run --memory-swap=1g nginx
Best Practice: Always set resource limits in production to prevent noisy neighbors.

Restart Policies – Self-Healing

Automatic container recovery

Restart policies determine what happens when a container exits.

no (Default)

Never restart.

always

Always restart if container stops.

$ docker run --restart=always nginx

unless-stopped

Restart unless manually stopped.

$ docker run --restart=unless-stopped nginx

on-failure

Restart only on non-zero exit code.

$ docker run --restart=on-failure:5 nginx

Container Timeouts – Stop & Kill

Graceful shutdowns

Containers receive signals when stopping. Graceful shutdown allows cleanup.

# Graceful stop (SIGTERM, then SIGKILL after timeout)
$ docker stop container
# Stop with custom timeout (seconds)
$ docker stop -t 30 container

# Immediate kill (SIGKILL)
$ docker kill container
# Kill with specific signal
$ docker kill --signal=SIGQUIT container

Graceful Shutdown

Container receives SIGTERM → can clean up → exits. Default timeout: 10s.

Hard Kill

Container receives SIGKILL → immediate termination. No cleanup.

Copying Files – docker cp

Moving data between host and container

docker cp copies files/directories between the host and a container.

# Copy from host to container
$ docker cp /host/file.txt container:/app/file.txt
$ docker cp /host/folder/ container:/app/

# Copy from container to host
$ docker cp container:/app/log.txt /host/log.txt
$ docker cp container:/app/logs/ /host/logs/
Note: docker cp works on both running and stopped containers. It copies from the container's filesystem, not volumes.

Environment Variables – Configuration

Passing configuration to containers

Use -e or --env to set environment variables.

# Set single variable
$ docker run -e MY_VAR=value ubuntu env

# Set multiple variables
$ docker run -e VAR1=val1 -e VAR2=val2 ubuntu

# Use env file
$ docker run --env-file .env ubuntu

# Override from host env
$ export MY_VAR=value
$ docker run -e MY_VAR ubuntu

Env File Format

# .env file
DB_HOST=localhost
DB_PORT=5432
DB_USER=admin

Container Security – Running as Non-Root

Least privilege principle

By default, containers run as root. This is a security risk.

# Run as specific user
$ docker run --user 1000:1000 ubuntu whoami

# Run as user from Dockerfile
# Dockerfile:
FROM ubuntu
RUN useradd -m -u 1000 appuser
USER appuser

Best Practices

  • Use USER in Dockerfile
  • Use --user when running
  • Drop capabilities (--cap-drop)
  • Use seccomp/AppArmor profiles

Risks

  • Root in container = root on host (if escaped)
  • Can modify host filesystem
  • Can install packages

Container Capabilities – Fine-Grained Security

Grant only necessary permissions

Linux capabilities break down root privileges. Docker drops most capabilities by default.

# Drop all capabilities and add only needed
$ docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx

# Common capabilities
# NET_BIND_SERVICE – bind to privileged ports (<1024)
# SYS_TIME – set system time
# NET_ADMIN – network administration
# SYS_ADMIN – dangerous, avoid

Recommended

  • Drop all: --cap-drop=ALL
  • Add only essential: --cap-add=NET_BIND_SERVICE
  • Never add SYS_ADMIN

Use Case

Nginx needs NET_BIND_SERVICE to bind to port 80. All other capabilities are dropped.

Health Checks – Monitoring Container Health

Ensure containers are working

Health checks allow Docker to monitor container health and take action.

# Dockerfile healthcheck
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost/ || exit 1

# Run with healthcheck
$ docker run --health-cmd="curl -f http://localhost/ || exit 1" nginx

Health States

  • starting: Initial state
  • healthy: Container is working
  • unhealthy: Container failed health checks

View Health

$ docker ps --filter "health=healthy"
$ docker inspect --format='{{.State.Health.Status}}' container

Pausing Containers – Freezing Processes

Suspend container processes

docker pause freezes all processes in a container using cgroups freezer.

# Pause a container
$ docker pause container

# Unpause a container
$ docker unpause container
Use Cases:
  • Temporarily suspend a container to free resources
  • Debugging without terminating processes
  • Migration / live migration scenarios

Important

Paused containers consume memory but no CPU. docker stop will fail on paused containers.

Exporting Containers – Filesystem Snapshots

Extract container filesystem

docker export exports a container's filesystem as a tar archive.

# Export container filesystem
$ docker export container > container.tar

# Export and compress
$ docker export container | gzip > container.tar.gz

# Import as image (flattened)
$ docker import container.tar myapp:flat

Use Cases

  • Backup container state
  • Debug container filesystem
  • Create flattened images

vs docker save

docker export is for containers (filesystem only).
docker save is for images (layers + metadata).

Managing container logs

Logging Drivers

  • syslog – syslog server

Container Labels – Metadata Management

Organize and filter containers

Labels are key-value pairs used to organize and filter containers.

# Add labels when running
$ docker run -d --label environment=production --label version=v1 nginx

# Filter containers by label
$ docker ps --filter "label=environment=production"
$ docker ps --filter "label=version"

# Inspect labels
$ docker inspect --format='{{.Config.Labels}}' container

Use Cases

  • Environment tagging (prod/staging/dev)
  • Version tracking
  • Team ownership
  • CI/CD pipeline tracking

Filtering

Use labels with docker ps --filter, docker rm --filter, and in orchestration.

Container Updates – Rolling Updates

Upgrading containers

Containers are immutable – update by replacing the container with a new one.

# Stop old container
$ docker stop web-v1

# Remove old container
$ docker rm web-v1

# Run new version
$ docker run -d --name web-v2 --restart=always nginx:1.21

Blue-Green Deployment

  • Run both versions side by side
  • Switch traffic to new version
  • Stop old version after testing

Rolling Updates (Swarm/K8s)

Orchestrators handle rolling updates with zero downtime:

  • Swarm: docker service update --image new
  • Kubernetes: RollingUpdate strategy

Container Rollback – Reverting Changes

Revert to previous version

Rollback is simple – just run an older image tag.

# Current version
$ docker run -d --name web --restart=always myapp:v2.0

# Rollback to v1.0
$ docker stop web
$ docker rm web
$ docker run -d --name web --restart=always myapp:v1.0
Best Practices:
  • Always tag images with semantic versions
  • Keep previous versions available
  • Use docker images to list available versions
  • Test rollback procedure regularly

Container Troubleshooting – Common Issues

Debugging containers

Container Exits Immediately

  • Check logs: docker logs container
  • Process might crash on startup
  • Use -it to debug
  • Check entrypoint/CMD

Port Already in Use

  • Check: netstat -tulpn | grep :8080
  • Use different host port
  • Stop the conflicting container

No Space Left on Device

  • Clean up: docker system prune -f
  • Check volumes: docker volume prune
  • Increase disk space

Permission Denied

  • Check user: --user
  • Check volume permissions
  • Use chown in Dockerfile

Container Best Practices – Production Readiness

Building production-grade containers

Do's

  • Use minimal base images (Alpine)
  • Run as non-root user
  • Set resource limits
  • Use restart policies
  • Implement health checks
  • Use volumes for persistence
  • Log to STDOUT/STDERR

Don'ts

  • Don't run as root
  • Don't store data in writable layer
  • Don't use latest tag in production
  • Don't embed secrets
  • Don't ignore resource limits
  • Don't disable logging
Key Principle: Containers should be ephemeral, stateless, and immutable.
